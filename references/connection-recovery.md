# 连接故障分层与恢复

用于用户报告连接失败、503、断流、`error decoding response body`，或旧请求超时后无法继续。只处理当前通道与请求，不顺带调整策略或全局网络配置。

## 先确定哪一层失败

| 层级 | 最小证据 | 能支持的结论 |
|---|---|---|
| Codex 对话请求 | 指定线程的错误、同一时段的客户端请求日志 | 503/high demand 是服务端报告不可用或过载；通用 network error 不能单独证明本机断网 |
| 本机到朋友服务器 | 现有入口一次 check/status 的返回、耗时、SSH退出码 | 成功说明当次SSH及命令路径可用，不说明模型完成 |
| 服务器到模型服务 | 当前request_id的API派发、首字节、终态时间与退出码 | 有首字节只说明响应开始；不代表收到有效正文，也不能排除后续传输问题 |
| 请求状态管理 | pending、receipt、会话锁、匹配进程、公开输出 | 识别仍在运行、可取回结果，或已结束但 unknown 阻塞接续 |

有明确服务端503时，不以重装、改代理、改DNS、切模型作为默认修复。服务端更深层原因未知就保留未知；Codex服务错误与远端Claude超时不能未经证据合并成同一原因。

先读既有恢复记录，避免重做无变化的检查。读取长线程时，先在工具侧筛选最新公开消息、错误和相关命令；单轮历史可能很长，即使turnLimit=1也不应整段回显。只提取请求阶段、状态码、时间和公开输出；不要输出密钥、请求原始头、私有推理或整个调试日志。日志中的普通数字（如504）不是HTTP状态证据，须确认其结构和上下文。

## unknown 的安全出口

unknown 防止重复调用是必要保护；缺少确认终止后的出口，会让已结束的请求永久挡住后续任务。在用户已有修复/接续授权内，由唯一写入者处理，不要求用户为同一修复重复授权。

解除前须同时确认：

- request_id、session_id、prompt哈希与原件一致；回执明确记录本地调用已结束，且没有完整结果可直接收取。
- 可获取会话排他锁，且无匹配请求/会话的进程；检查与写入resolution期间保持锁。仅超时或仅锁空闲均不足够。
- 公开会话记录能匹配原请求；没有可恢复的公开答复。有答复先收取，不能丢弃后重调。
- 没有未核清的外部副作用。源案例禁用了远端工具；工具可执行的任务还须核清已发生的写入/操作，不能把“无公开答复”解释为“没有执行”。

保留原请求与unknown回执，另外写入恢复记录：绑定请求、会话、prompt哈希和原回执哈希，记录确认依据、时间及授权范围。成功持久保存后才归档pending、解除这条记录的阻塞；处理必须可重复查询，并能在远端resolution已写入、本地归档中断时从原记录收尾，不能重新调用模型。发现内容或身份变化就停止该恢复动作。

`confirmed_terminated_no_public_result` 只表示旧客户端调用已结束且无公开结果可取，不声称模型从未处理请求，也不把原unknown改写成failed/completed。项目若只有固定ID恢复入口，复用其检查，仅针对本次证据扩展；不要把历史许可范围当作所有任务的默认授权，也不要自动跳过全部unknown。实现新入口时，保留备份并核对运行中代码，不能直接覆盖其他写入者的新版本。

恢复后按用户/主管已有授权处理下一步：先提交必要的短增量，请主管返回下一条可执行安排；不要自动复制整段旧任务作为新请求。新UUID代表新调用，不叫原请求重试成功。若确实要重做原业务任务，另记attempt并保留旧失败。

## 减少复发与扩大损失

- 不能保证避免服务端过载。遵循服务端建议或客户端现有退避；已有请求先查状态，不叠加手工重试和定时任务重发。
- submit与耗时模型执行分离，先持久保存请求身份，再异步执行、按ID收取。用户界面断流不触发第二次模型调用。
- 不盲目延长超时、切换模型或新建会话。短接续消息减少重复材料，但不是已经证明的过载修复方法；仅见长上下文或max档位不能判定它们是根因。
- 恢复期间只有一个主管写入者。向原聊天交接须有用户授权；交接写明当前request_id、谁负责收取、是否可提交下一条，别让两个聊天同时推进同一请求。
- 修复后一次实际接续仍以相同方式超时，应保留新请求并报告剩余故障，不循环“解除unknown→重发”。不受影响且已授权的文件接收可继续。

分别报告：入口可达、遗留状态已处理、已提交/started、已取得完整公开答复、已执行任务。只有相应证据支持时才使用相应措辞；原Codex重新输出一条消息也不证明Claude回复完成或服务持续稳定。
