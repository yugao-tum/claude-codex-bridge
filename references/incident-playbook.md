# 真实故障与下次处理

本页保留 17 类历史桥接故障，并补充 5 类直聊实践；复现故障、静态发现、预防措施和实际端到端观察分别注明。遇到相同症状先定位案例，再读取链接中的操作细节；不要求正常聊天每轮执行整张清单。数字是历史证据，预算、模型、并行度仍取当前授权。

## 1. 连上宿主机不等于找到了模型执行层

- **实际情况**：宿主账号看不到 `claude`；模型在容器账号内。后来从旧 `deploy-app-1` 迁到 `wb <container-profile>` 专用入口，HOME、workspace、transcript 位置随之改变。
- **处理**：从已授权入口确认容器、执行账号、绝对 binary 和持久目录；恢复时让 session marker、transcript、请求回执对应原 UUID。旧 Pi planning 通道与 Claude Code 固定会话不是同一上下文。
- **下次避免**：记录实际链路及版本，复用现有入口。不能因为“命令不存在”改朋友的默认客户端，也不能用新 session 假装恢复。已知 `probe-conversation.py` 仍指旧路由，勿按文件名猜用途。
- **证据边界**：历史约 8 分 37 秒后成功取回说明当时 SSH 脱离机制可用，不证明整机重启后计算继续。详见 [transport](transport.md)、[local-binding](local-binding.md)。

## 2. 把三种超时当成一个网络问题

- **实际情况**：源记录同时出现 Codex 服务端 503/响应体解码失败、SSH banner exchange timeout、远端 Claude 900 秒 `exit 124`。这些发生在不同层；一次 SSH 收取失败后，同 request_id 后来已完成。
- **处理**：先定位发错的一层，保留短错误、时间和原 ID。Codex 无输出不等于服务器无输出；55 秒本机等待到期只改为查原 status。主管基础 900 秒和 worker 自带预算分开。
- **下次避免**：不要凭错误名改代理、认证、服务器或模型，不把 ready/check 当模型恢复。先收原结果，网络恢复后继续原任务。
- **证据边界**：历史 check 约 4.5 秒、另一次首字节 1259ms，不能解释之后某次零正文超时的根因。详见 [connection-recovery](connection-recovery.md)。

## 3. unknown 卡死：既不能删 pending，也不能永远停在“不能重发”

- **实际情况**：客户端已结束、无可恢复公开结果，但旧 unknown 仍占主管会话。后来增加独立 resolution，未覆盖原 unknown。
- **处理**：匹配原 ID/hash/session；在**持有主管排他锁期间**确认无匹配进程、公开 transcript/输出无完整答复、无未处理外部副作用；保存证据和原回执 SHA，另写不可覆盖的 `confirmed_terminated_no_public_result`。远端记录落稳后归档本机 pending。中途断开先收已存在 resolution。
- **下次避免**：`connect.py resolve-terminated` 只支持实现中两条历史 UUID。新请求不能替换为旧 ID 或批量解锁；在已有修复授权内针对事实扩展。解除后发下一条获授权增量，不自动重发整个旧问题。
- **证据边界**：只证明本轮已确认终止且没有公开结果；不证明后端未处理、未计费。相同超时再次出现须报告，不循环清理重试。完整条件见 [connection-recovery](connection-recovery.md)。

## 4. not_found 不能直接解释为没有调用过

- **实际情况**：另一条 pending 用 `resolve_77f4_not_registered.py` 单独处置，原因是原请求未登记，和案例 3 不同。
- **处理**：正确路由下持有原锁，确认 request/receipt 均不存在、无匹配进程、transcript 无对应公开 user prompt SHA，保存 `confirmed_not_registered_no_public_user_prompt_no_matching_process` 与本机原件。
- **下次避免**：单独 `not_found` 或锁空闲不够。若需要恢复提交，必须由唯一写入者保留原 ID/正文/参数，不能调用会生成新 UUID 的普通 chat 代替。
- **证据边界**：该处置脚本未调用模型，不是通用清锁入口。详见 [request-lifecycle](request-lifecycle.md)。

## 5. completed 与大段正文不保证完整文件

- **实际情况**：早期 W1 返回约 36,304 字符，正文仍从半段代码开始；另有 W3 900 秒没有公开正文。取回原始文件后才能分清界面截断与模型输出缺失。
- **处理**：原文先留档；完整文件继续承接，不完整文件不猜补。主管决定缩到单文件/小文件组、使用 diff 或新 attempt。记录谁要求的修复及次数。
- **下次避免**：派发时选与接收器一致的输出协议。v1 旧桥 completed 的判定弱于主管桥，不擅自声称验证了所有型号/session/文件。格式修复预算与执行超时预算分开。
- **证据边界**：桥返回、文件落地、命令运行、用户验收分别报告。详见 [parallel-execution](parallel-execution.md)。

## 6. 多个 worker 零正文不是“prompt 太大”或“没有消耗”

- **实际情况**：六条任务在预算边界退出：900→905.358/905.350 秒 `-9`；1200→1206.767/1206.427 秒 `-9`；1800→1800.414 秒、1500→1500.560 秒 `124`。一条仅 1501 字符仍失败。
- **处理**：保留原 stdout、预算、实耗、退出码。`timeout -k 5s` 支持“124 贴预算 / -9 贴预算+5–7 秒”的预算终止解释；`resume_dispatch.py` 仅在预算至预算+15 秒内将 -9 标为 `deadline_kill_consistent`，提前 -9 仍属原因未知。
- **下次避免**：状态查询不算新 attempt；不能把网络不确定、预算终止、格式缺失共用一个重试计数。历史两半各 2400 秒恢复是主管明确指令，再失败即停该阶段，不继承为任意任务增时授权。
- **仍未知**：排队、首响应等待、推理、资源竞争各占多少，未被当时 JSON 最终输出模式观测到；空 stdout 不证明零 token 或 OOM。来源：`remote-failure-retrospective-20261013.md`。

## 7. v2 改善公开输出可见性，但没有证明大任务时延已解决

- **实际改动**：新 `implementation-v2` 使用 `stream-json --verbose --include-partial-messages`；首公开 text 最长 300 秒，总时限独立；最多两个 Python 文件、总公开文本 12000 字符。即时保存 `public-partial.txt`，完整对象需路径合法、`# END <path>`、AST 通过，才进入 `recoverable-files.json`。
- **处理**：仅明确启用的新任务走 v2；旧 v1 在途任务按原入口和预算收取。部分尾部文本不是可执行文件，恢复文件也不自动覆盖项目。
- **下次避免**：thinking/signature/control 不作为公开进度；收首公开 text 与首 HTTP 字节分开。总预算先到先终止；仅清理本任务进程组，不自动重发。
- **证据边界**：真实 Fable/high canary 120 秒预算，首公开 1.917 秒、总 3.682 秒，tiny.py 完整；只证明小文件链路。不得依据旧交付文档“未部署”忽略后来的 canary，也不得据此宣布大型任务成功。详见 [parallel-execution](parallel-execution.md)。

## 8. 工具 session 返回不代表后台继续跑

- **实际情况**：本机 driver/finalizer/guard 后来都不存在，计数停在 1183；接收器状态也停在 08:10。没有证据知道是谁结束了进程。另一次进程查询受权限影响，后来精确 CIM 查询确认进程仍存活。
- **处理**：检查 PID+开始时间+命令、状态更新时间、实际进度，先区分查询失败与确实不存在。确认结束后用隐藏独立进程承接原脚本、原 t0、原计数/数据/预算，不开第二份任务。
- **下次避免**：不能长期保存 PID 作为存活证据；恢复不重置原 6000 请求上限或时间窗。S2 心跳 helper 仅准备给下一次启动，不冒称已装到当前运行进程。
- **证据边界**：历史恢复后跨工具调用仍存活，计数 1183→1817，原 88 份文件 SHA 不变；没有系统重启验证，也没新增开机任务。详见 [runtime-recovery](runtime-recovery.md)。

## 9. 收件断线后查询轰炸、已结束任务从汇总消失

- **实际修复**：接收器锁防重复；本地 terminal receipt 直接保留，剩余任务先用一个原请求探测共享 SSH，可用才并行最多 3 个查询。正常 45 秒，断线 60/120 秒退避，连续 3 次停本轮 collector，保存 pending。
- **下次避免**：`needs_connection_recovery` 是接收器状态，不能写成远端任务 failed；一小时收取窗到期也不杀远端。重启从各原 task/receipt 恢复终态，不重新 submit；现脚本限特定批次路径，不是通用队列。
- **证据边界**：历史五项针对性检查覆盖断线、终态保留、成功重置错误数、终态不远查、提前 -9 不错判。此次技能整理未重跑运行测试。详见 [runtime-recovery](runtime-recovery.md)。

## 10. 用户说换远端主管，Codex 却查自己的模型目录

- **实际情况**：用户明确要求远端 Fable 5.1 临时主管；曾误查 Codex 型号并重复追问。后来修改项目 bridge 的实际 `MODEL` 路由，并同步本机请求归档标签，保留同一 session/max。
- **处理**：按上下文识别模型所属角色；在原锁和无在途请求的条件下备份、修改获授权的项目入口。只有 prompt 或归档标签变了都不算实际切换。
- **下次避免**：历史模型窗口到 2026-10-13 20:45 China；额度/心跳冲刺到 20:59，两个截止不能合并。`activate_fable_supervisor_window.py` 是一次性脚本；旧前台标题 Opus 不证明实际路由。
- **证据边界**：部署回执证明条件切换已布置，不能证明到期后已读回切回；型号回显也不独立证明供应商底层身份。详见 [model-and-capacity](model-and-capacity.md)。

## 11. auth/help 没显示额度，被误说成无法查询

- **实际修复**：隔离诊断 PTY 运行内置 `/usage`；不 `--resume` 主管，也不 `claude -p "/usage"` 让模型回答账户额度。脚本输出中结构化 remaining/reset 为 null 时，实际公开屏幕行仍可能有值。
- **交互坑**：信任确认页盲按向下键曾把 Yes 改为 No。解析 ANSI 和空白后仍保留选中标记，确认实际页面与已授权目录再按键；仅清理诊断自己的进程。
- **下次避免**：按窗口报告原 used、`100-used` 的 remaining、查询时刻与时区；不显示的 session reset 写未知，不复制旧数值。21/28/4% 是当时已用示例，不是剩余，也不是现在账户状态。
- **证据边界**：内置额度、单请求 usage、会话累计 modelUsage、Codex 账户是不同口径。详见 [model-and-capacity](model-and-capacity.md)。

## 12. 桥接正确，运行入口却错了，整批没有有效结果

- **目录**：某批十个子任务都因外部 userdir 不存在启动失败。按主管指令建必要目录后，每 cell 一次获授权重试才成功；旧失败不回写为成功。
- **参数**：某版本任务运行器的 datadir 配置路径未按预期生效，空默认目录引发大批下载和 50011 限流；实际入口显式传 `--datadir` 修复。userdir/dbpath 被 wrapper 覆盖，绕过 wrapper 又可能复用旧 DB。下次确认实际 argv 和入口，而不只读配置文本。
- **清单**：聚合任务引用旧 manifest，改输入指针后可重聚合已有结果，无需重做计算；两个目录代码相同、说明文件不同，也不据目录名强制全部重跑。
- **读取**：SQLite `mode=ro` 仍可能涉及共享内存文件，确需不触动运行库的分析使用一致快照。不要把“只读 SQL”扩大成“文件绝不变”。
- **下次避免**：把主管已给的 source manifest、数据目录、输出目录、运行入口写进任务交接，只处理本轮运行所需条件，不启动全库审计。
- **证据边界**：这是版本和入口相关案例，不是所有框架的永久规律；启动成功、离线计算测试不等于业务验收。来源：`claude-progress-report-20261013.md`，步骤见 [runtime-recovery](runtime-recovery.md)。

## 13. “主管记得目标”不保证目标没有被改写

- **实际情况**：Claude 能复述目标，却把用户要求缩窄到特定条件下才适用，并承认这是自己的解释。用户后续明确修改目标及比较口径。
- **处理**：传递用户原话及日期、用户明确修改、尚未采纳的主管建议三栏。建议可以继续讨论，不能当用户已授权修改目标；也不把旧项目目标和业务参数固化到通用 skill。
- **下次避免**：Codex 不引导主管钻局部优化，发现目标表述不一致时传递差异原文，不替双方创造折中目标。最新职责“只桥接”覆盖旧“Codex 主控并咨询”。
- **证据边界**：该对齐不构成自动审计或额外业务门槛。模板见 [message-templates](../assets/message-templates.md)。

## 14. 普通修复反复阻塞用户，或越过真正授权边界

- **实际情况**：Windows 时钟同步曾被升级成持续阻塞；用户已授权服务同步和替代时间核对，并要求不要再因此停住。另一方面，删除/重建整份外部任务状态目录曾被自动审批拒绝，后来才有用户明确授权。
- **处理**：已获授权的低影响修复和替代执行由 Codex 立即落地；不把同一答案反复问用户。停止旧目标、暂停项和已给授权随交接保留。
- **下次避免**：操作不便不自动成为业务门槛；“自动修复”也不覆盖删除、资金、隐私和范围变化。实际审批拒绝明确说明动作和原因，保留现场，不偷偷换手段。
- **证据边界**：授权来自当前任务，不从历史案例推导其他项目权限。

## 15. 实时窗口、归档、直接聊天是三项不同能力

- **实际情况**：`foreground_view.py` 能显示公开增量，关闭再开可追尾；没有读取用户 stdin。只显示窗口不代表已经存全档。旧 archive 白名单也不含 usage/attempt/source_manifest/v2字段；自动远端同步仍不完整覆盖 v2。
- **处理**：保留原任务、回执、公开 partial、recoverable files；简化对话归档用于阅读，原件用于恢复。模型来自当次 request/response，不用固定 banner 代替。
- **后续实现**：包内独立直聊使用新 session 和 MCP 本机工具，没有 GPT 消息转述；旧 foreground viewer 本身仍无输入能力。不要并开原生 `claude --resume` 抢主管会话。
- **证据边界**：已验证的独立直聊与旧主管共用队列是两件事；后者未实现，自动排队和任意自然语言自动执行也未提供。详见 [operations](operations.md)、[direct-chat](direct-chat.md)。

## 16. 并行承接与主管单写入不能混为串行全部工作

- **实际情况**：单项归档曾拖住全部接收；用户要求高并行。收件、本机落地、不同文件实现可以独立处理，主管持久会话仍只有一个写入者。
- **处理**：主管分任务、独立 worker SID、明确文件归属；结果到一项接一项；跨线程只读查看不等于已移交。交接列原 request/pending、尚未转达原话、预算和 worker terminal 状态。
- **下次避免**：不让所有工作等待最慢 worker，不让新线程因“看到授权历史”自动抢原主管；已有明确持续授权下也不要每轮等用户催。
- **证据边界**：同时 8 worker 是当时获授权冲刺规模，不是技能默认并发。详见 [parallel-execution](parallel-execution.md)。

## 17. 计划、调用和交付被混说成已经完成

- **实际情况**：Grok/Antigravity 在本机可用，但计划预算不等于已调用；Git 同步节奏与心跳恢复建议也不等于已创建或已执行。
- **处理**：反馈分别写计划、已提交、已返回、已落地、已运行。工具按主管索取的信息缺口使用；远端禁工具时补文本，不说它已自主读过仓库。
- **下次避免**：同步给主管的是本轮必要 commit/源码清单，不为每句对话 push/pull，也不外发原始数据或运行库。目标改变后更新既有 heartbeat 的目标、owner和停止条件，实际修改调度必须有对应授权和工具回执。
- **证据边界**：交付只报告本轮达到的层级。耗尽额度、增加轮次、模型说完成都不能代替用户可用结果。

## 18. 直聊终态与进程清理错位，旧线程影响新请求

- **离线复现**：先把状态置 completed、后清理旧进程，可能让新 send 进入后被旧 finally 清空 proc。另一种是旧 connection watcher 延后唤醒，设置共用 cancel_event，误取消新一轮；断线后缓冲中的文件 tool_call 也曾仍被派发。
- **修复**：done 先进入 finishing，turn_running 守住完整生命周期；finally 仅清自己的 proc。观察线程持锁核对 proc 与 request_id 后才通知取消；工具派发同时检查 stopping/cancel_event。recover 拒绝并行恢复并核 request_id 后回写。
- **审批/停止**：审批只对应当前 call_id，布置审批与停止信号在同一锁内协调；连接尚未建成也能记下取消。不得把恢复状态当重新发送。
- **证据边界**：竞态由离线状态机测试复现后修复；真实聊天连续三轮已完成，不代表真实断网、休眠及长期并发压力已验证。

## 19. 首轮失败被误认为已建立可恢复会话

- **静态发现**：收到 ready 就把 session_started 写 true，会让首次调用没有生成 transcript 的失败被下一轮错误地 --resume；ready 只说明通道开始工作。
- **处理**：远端检查持久 transcript，并通过 ready/done 的 resume_available 返回接续能力；本机不把 ready 等同于会话已建立。缺字段时保留旧状态，旧成功 done 可兼容为 true。
- **恢复边界**：首次失败只有在前次已明确终止且无 transcript 时，才可由下一条用户新请求在同一独立 SID 初始化；状态 unknown 不自动初始化或重发。
- **证据边界**：这是静态识别并通过模拟回归验证的缺口，真实联调首轮成功；不能声称生产中已复现首轮失败。

## 20. 系统提示快照与工作目录提示的时效

- **预防性判断**：续聊可能保留初始系统提示快照，不能只改变本机 workspace 标签就假定远端收到新的目录/分工约束。
- **实现**：专用 CLI 接受 --system-prompt-snapshot off；每轮 --append-system-prompt 传本轮选定工作目录、四工具职责、项目说明读取要求和命令审批边界，使用 --setting-sources "" 隔离意外全局说明。
- **证据边界**：参数支持和同 SID 真实续聊已验证；没有真实复现“旧系统提示导致错误”，也未实测切换工作目录后的提示更新。目标 CLI 不支持该参数时应明确适配，不静默去掉后仍宣称等效。

## 21. 命令审批不等于操作系统沙箱

- **实际界面**：审批卡显示完整命令、cwd 和 timeout_seconds，仅允许一次或拒绝；不保存全局自动批准。文件读写按选定根目录和路径检查限制，覆盖时保存备份。
- **权限边界**：获准 PowerShell 命令按 Windows 用户权限执行，可以访问 cwd 以外的账户可访问资源。目录限制、凭据文件过滤、备份都不把命令变成 OS 沙箱；需要系统级隔离时另行选择执行环境。
- **实测**：本机简单文件读取、写脚本、一次批准后执行并得到预期结果/退出 0；另一轮拒绝命令后 Claude 未重试或换方式。原文内容、会话 ID、测试标记和截图未放入公开包。
- **局限**：这是指定命令和拒绝情景的观察，不保证任意命令安全，也不保证任意内容过滤都能识别所有秘密。

## 22. Grokbot 专有执行通道不能假装是通用 MCP

- **只读发现**：Grokbot 0.70.2 的本地包包含账户、machine 和 approval 绑定的 GET SSE /local-exec/requests、POST responses/connection 调用形态；未看到本机 TCP listener，也未找到可直接复用的开放 stdio MCP/API。
- **决策**：未读取或解封凭据、未修改应用。包内直聊自建最小 MCP relay，不依赖 Grokbot 私有账号接口，不冒充已有第三方集成。
- **边界**：“未发现开放复用接口”不等于协议永不能复用。以后若有官方文档、公开接口和相应授权，再单独评估；不要从打包代码中的 URL 猜出可用认证或通用命令。
