# 本机运行与持续承接

用于工具 session 消失、后台进度停滞、receiver 断线、进程不可见，以及接续已授权的长任务。只处理本次运行身份、状态、路径和预算，不扩成业务审计。远端请求状态见 [请求协议](request-lifecycle.md)，按具体症状选择动作见 [事件处理手册](incident-playbook.md)。

## 1. 先分清哪个东西结束了

`exec_command` 返回的工具 session 是交互句柄，不是后台进程生命周期保证。工具句柄失效、SSH 断开、本机 receiver 退出、远端模型到期是不同事实，不能互相推断。

源 2026-10-13 有两种不同事件：

- 下载的原 driver/finalizer/guard 已不在，计数停在 1183，旧工具 session 无法接回；原 receiver 的进程也消失。原因未知，不能断言是终端回收或系统杀进程。
- 后来一次普通 `Get-Process` 没看到仍在运行的下载 PID。获准的精确 CIM 查询看到同一进程和子进程，counter 继续增长。这是检查上下文可见性差异，不是又一次进程消失，不能据此重启。

遇到“看不到”先对照原记录、状态时间和实际进展；权限不足时报告观察受限，在已有授权内使用足以观察该目标的查询。不要遍历或输出用户全部进程，也不要因一次空查询就启动第二份任务。

## 2. 运行证据保留三层

| 层级 | 最小字段 | 能证明什么 |
|---|---|---|
| 进程身份 | PID、开始 UTC、命令/脚本路径、所属任务；必要时父子关系 | 找到的是本任务进程，避免 PID 复用或启动壳已退出 |
| 状态与存活 | 状态文件更新时间、写入者身份、进程锁、最后心跳、退出回执 | 当前观察或最近一次观察的存活/结束，不等于业务有进展 |
| 实际进展 | 原 counter、结果回执数、最后请求进展时间、最后结果进展时间 | 请求活动或成果新增；请求增长不等于每次成功，进程退出 0 不等于业务验收 |

长任务状态应区分 `last_progress_utc` 与 `last_result_progress_utc`。读到正在写入的 JSON 而暂时无法解析时，保留上一次有效进展，并记录本次字段不可读；不能把计数变成零或宣布任务停止。

按状态提供判断需要的最少事实：目标进程是否可观察、状态最后更新时间、进展是否增长、是否到原截止、接下来收件还是恢复。不以启动时的一张 PID 回执永久宣称“仍在运行”。

## 3. 已授权长任务脱离工具交互继续运行

复用项目已有 wrapper；后台启动使用 `Start-Process -WindowStyle Hidden`，记录实际工作进程身份和运行目录。只取得启动壳 PID 不够，还要接回它启动的工作进程或真实退出回执。标准输出与脱敏错误落指定本地文件。

源接收入口 `<BRIDGE_DIR>/run_fable_receiver_detached.ps1` 调用 `receive_fable_60c_workers.py`，完成或异常写 `receiver-exit-20261013.json`。它硬编码旧六项任务，只能作为实现参考或接回这些原任务，不能在新批次直接运行来接收任意 worker。

启动前核清原进程与锁。使用进程持有的排他锁防重复，不靠删除锁文件或看到旧 PID 消失就认定可以抢占。已有活跃写入者时保持其归属；锁空闲本身也不证明远端请求没运行。

恢复下载、计算或收件时沿用原任务身份、计数、数据目录、原 `t0` 和停止预算；保留原结果与失败。读取现有 manifest/指纹仅为确认恢复同一份输入，不重新审计全部数据。不要因为重新启动 wrapper 就清零 HTTP 次数、重新给足两小时、换数据路径或重复已完成单元。新 attempt 或延期须来自已有用户/主管授权。

源下载恢复保留原 88 份数据指纹、counter 和 `t0`，在原预算继续；这证明了该次恢复，没有证明跨系统重启可自动恢复。后台进程、心跳与系统级开机任务不能混称。

## 4. 结果接收器的有限循环

源 `receive_fable_60c_workers.py` 已实现以下行为，参数是该次运行安排，不是所有项目默认：

1. 接收明确列出的原 task 文件；所有查询使用原 request ID，从不 submit。
2. 已有 `completed/failed/cancelled/rejected/not_registered` 终态回执直接读本机，不再次查询远端；终态保留在总汇中，不能因本轮不再轮询而消失。
3. 每轮先查一个未决请求，确认共享 SSH 通道可用，再以最多 3 路并行收其余状态。网络故障时不让全部 worker 同时反复探测同一通道。
4. 正常等待 45 秒；连续连接失败后分别等 60、120 秒。成功一轮清零连续失败计数。
5. 连续三次 `transport_unknown`，保存所有已收状态和未决清单，写 `needs_connection_recovery`，结束本轮 collector。**只停收件器，不取消远端 worker、不改失败状态、不重新派发。**
6. 本轮接收有一小时边界；结束留下退出原因。恢复时先核旧 receiver 的进程身份、状态、锁，再接原未决 ID，避免两个接收器重叠。

汇总至少含检查 UTC、receiver PID/身份、receiver 状态、连续连接失败数、pending task 列表和全部已观察 worker 状态。`failed` 的执行退出码与 `transport_unknown` 的连接失败分栏保留；判断 124 或 -9 是否预算终止，要对照原时限和实际耗时，不能把提前 -9 一律算超时。

源接收器已有五项针对性测试记录：三次连接失败有界停止、不丢终态且不重复查询、恢复清除失败计数、终态回执不请求远端、提前被杀不误判超时。这只覆盖这些行为；不代表远端服务稳定、长期接收无丢失或跨重启恢复通过。

对属于本批次的任务，实际入口形态是：

```powershell
py -X utf8 "<BRIDGE_DIR>/receive_fable_60c_workers.py" <原任务JSON绝对路径> ...
```

尖括号替换为已保存原任务路径，不是字面参数；当前脚本限定任务在 `parallel-implementation/resume-20261013` 下。状态文件是该批次 `FABLE-60c-worker-receive-status.json`，锁为 `receiver.lock`。该次 receiver 汇总在内存中累计，重启时由各原 receipt 恢复；没有通用持久队列。下一批不能原样使用旧 wrapper 的六个固定任务，也不能只改路径便假设 v2 能由此收取。

## 5. 心跳准备完成不等于当前进程已经启用

源 `s2-wrapper-heartbeat.py` 与相应 recovery wrapper 是后续启动版本：持有单实例锁，立即写首条心跳，之后每 60 秒更新；PID 加开始时间确认身份。当前正在下载的旧进程没有因此被重启，也没有自动装入助手。

报告时分清“代码和本地检查完成”“下一启动生效”“已实际启动并观察”。不能为证明新助手生效而额外启动第二份下载，或把不存在的实时心跳说成已有证据。下一次获准启动时再由负责执行者启用，并继续原任务预算和进展记录。

## 6. 运行前落实已给指令中的必要路径和版本

这一步是机械落实执行条件，避免把环境失败当作业务结果，不另设业务放行关卡。沿用当前项目与主管规定，遇到新规则缺口再交主管；不要照搬源项目目标、预算或数据范围。

| 已明确的运行条件 | Codex 直接落实 |
|---|---|
| 解释器和依赖 | 用已指定项目解释器并记录 `sys.executable`；源案例 `-I` 会隔离所需项目环境，不因习惯添加它 |
| 输出目录、userdir、临时目录 | 启动前建立该任务需要的目录；要求不存在的测试临时目录使用新路径，不复用运行状态目录 |
| datadir | 按实际程序接受的入口传入绝对路径；源案例配置中的 datadir 未被采用，最终使用 CLI `--datadir`，不能只检查配置文字 |
| userdir、DB 路径 | 参数指向主管指定的任务/STATE 目录；不依赖默认 cwd，不把运行 DB 写进源码或部署树；不输出凭据 |
| 版本和输入 manifest | 让实际代码 commit/部署版本、配置、数据 manifest 对应同一次运行；复用已给版本标识，不把代码、标签和回执拼成不同版本 |
| 预算与截止 | 原 `t0`、累计次数、资源限额、停止条件与任务记录一致；恢复不会获得新预算 |

历史一批 10 次启动因未建外部 userdir 失败，未产生有效任务结果；另一次启动忽略配置 datadir，误用默认目录。应落实已要求的目录和启动参数，并记录实际路径；不需重做业务分析、额外全仓测试或请用户逐项确认。环境修复后的重跑次数仍受该轮主管已给额度约束。
